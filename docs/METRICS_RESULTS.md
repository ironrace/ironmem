## §1 — Claim under test

METRICS_SPEC §1.1 states the falsifiable claim verbatim:

> ironmem + planning discipline reaches **merged-and-passing** with **fewer rework loops**
> and **lower total tokens per task** than superpowers-alone, and stays smart in long
> sessions because durable server-side state makes `/clear` cheap.

The §11.3 sample-size floor (≥8 completed tasks per arm) is now **MET**: both arms
completed all 8 tasks (8/8 merged + CI-green). This result is therefore **reportable**
under the spec's stated confidence rule.

---

## §2 — Headline verdict

**Thesis NOT confirmed as a clean memory-vs-no-memory test on this corpus.**

The §1.1 claim requires a causal attribution of the token delta to memory. That
attribution **cannot be made** from this campaign because the two arms differ on two
confounding dimensions that prevent a clean memory-on vs memory-off comparison (see
§4). Neither exclusion of cache tokens nor stratification by model/provider closes the
gap; instead, they show that structural multi-actor workflow overhead is a likely major
contributor.

The outcome sub-claim is confirmed: **both arms reached merged + CI-green on 100% of
tasks** (outcome tie at 8/8). The `/collab` path demonstrably completes headlessly
end-to-end on real repo tasks — an operational result, even though it does not support
the §1.1 token-efficiency claim.

Because the spec §1.1 calls for the result to be "reported as written either way", this
document presents the measured numbers and the confound analysis honestly, not as a loss
or a win.

**Note on fix_commits=1 (ironmem):** Every ironmem task has `review_rounds=0` and
`fix_commits=1`. Because `fix_commits` is the counter for commits made during the
`CodeReviewFixGlobalPending` (rework) phase, and the `/collab` path always passes through
that phase even when there are no review findings, this +1 is a `/collab` squash-commit
artifact — not evidence of a review-driven rework loop. The METRICS_SPEC §4 wording says
"+1 per commit made during a rework phase"; a commit made in `rework` phase with zero
review findings still increments the counter. The reported rework_loops=1.0 should be
interpreted as a structural `/collab` protocol overhead, not as a quality signal.

## §4 — Confound analysis

The §2.1 headline (6.1×) is a real measurement, not an artifact — but it is **not
apples-to-apples** because the two arms differ structurally on two dimensions. Neither
of the two potential explanations (cache accounting or model choice) fully accounts for
the gap; and the dominant explanation (multi-actor workflow) is structural.

### Sensitivity table

| View | ironmem mean tokens | superpowers mean tokens | ratio |
|------|--------------------|-----------------------|-------|
| (a) Raw pooled §2.1 (cache-included, both providers) | 30,325,346 | 4,941,919 | **6.1×** |
| (b) Cache-excluded (input+output only, both providers) | 1,109,185 | 21,055 | **52.7×** |
| (c) Claude only, §2.1 (cache-included) | 19,809,632 | 4,941,919 | **4.0×** |

**Reading the table:** None of the three views is a decision-grade causal result; all
three show ironmem consuming substantially more tokens per task. The three views isolate
the contribution of specific confounds but cannot remove the workflow asymmetry.

### Confound 1 — cache_read accounting

The raw §2.1 total counts `cache_read_input_tokens` as real context processed (correct
per METRICS_SPEC §2.1; discounting cache reads is a cost concern, not a token-count
concern). The `/collab` workflow re-reads large cached contexts every turn, so cache_read
tokens dominate the ironmem §2.1 total (~10M Codex cache_read on one task alone).

**However:** excluding cache tokens (view b) widens the ratio to 52.7×. Cache _is not_
the explanation for the gap — removing it makes the disparity larger, not smaller. The
ironmem arm consumes substantially more fresh input+output tokens per task because the
multi-actor workflow generates many more turns of fresh context.

### Confound 2 — two-model / two-harness asymmetry

This structural asymmetry prevents causal attribution. The two arms are not matched on
workflow:

| Dimension | ironmem arm | superpowers arm |
|-----------|-------------|-----------------|
| Harness | `/collab start` (headless) | `claude -p` (single-shot) |
| Actors | Claude (planner/reviewer) + Codex (implementer/reviewer) | Claude only |
| Phases | v1 planning + v3 batch implementation + review | single prompt → done |
| Turns per task | many (planning → task loop → review) | typically 1–few |

The ironmem arm runs a full two-model orchestration protocol: Claude plans, Codex
implements (multiple worker turns), and Codex reviews. The superpowers arm is a
single-harness Claude invocation. The comparison measures **"full multi-actor workflow
vs single-agent skills"**, not a clean **"memory on vs memory off"** contrast.

View (c) — Claude-only §2.1 — shows the gap is 4.0× even when Codex tokens are excluded
entirely. Claude alone consumes 4× more tokens on the ironmem arm because it runs more
phases (planning, orchestration, review coordination) than the superpowers single-shot.
The remaining 2.1× on top of that (4.0× → 6.1×) comes from Codex.

**Conclusion:** Neither cache exclusion nor provider stratification produces a view that
can be interpreted as a memory-vs-no-memory comparison. The structural workflow
asymmetry is not correctable post-hoc from this dataset.

## §5 — CAN / CANNOT conclude

### CAN conclude

1. **Both arms reached merged + CI-green on 100% of 8 tasks.** Outcome quality is equal
   at this sample size. Neither arm abandoned or failed any task.

2. **The `/collab` path completes headlessly end-to-end on real repo tasks.** The
   campaign demonstrates that the headless collab driver can drive a `/collab` flow
   through planning, implementation, review, and PR lifecycle without human gates.
   This is an operational result independent of the token comparison.

3. **The raw token delta is real and large.** The ironmem arm consumed 6.1× more §2.1
   tokens per task on average (range 3.7–57×). Even after removing cache tokens the
   gap is 52.7×. These are accurate measurements of the actual token consumption for
   each arm as run.

### CANNOT conclude

1. **Cannot attribute the token delta to memory.** The arms are structurally unmatched
   (multi-actor workflow vs single-agent, §4). The token difference is not attributable
   to the presence or absence of ironmem as a memory backend from this design.

2. **Cannot confirm or cleanly falsify §1.1's "lower total tokens per task" claim.**
   To confirm or falsify it, the arms must be matched: same harness, same model, same
   number of actors — varying only whether the ironmem MCP server is present. This
   campaign does not satisfy that design requirement.

3. **Cannot claim rework_loops favors either arm.** The ironmem rework_loops=1.0 is
   a `/collab` squash-commit artifact (review_rounds=0 on all tasks; see §3.1 note),
   not a quality signal. With review_rounds=0 on both arms, the iteration-count
   sub-claim of §1.1 ("fewer rework loops") is neither confirmed nor falsified.

## §6 — Limitations and threats to validity

1. **Done proxy (METRICS_SPEC §12 2026-06-16):** "done" is agent-completed with the
   task's frozen gates green in the isolated workspace, recorded as `outcome:"merged"`
   and `ci_green:true`. This is the correct proxy per §2.2 but is not identical to a
   literal merge-to-main or business-value delivery time.

2. **Headless `/collab` vs full interactive session:** The ironmem arm ran through the
   headless collab driver. A real interactive session may spend tokens differently
   (user confirmations, re-directions). The headless mode is a reasonable surrogate for
   comparative measurement but not identical to the target use case.

3. **Codex cached-input subtraction (METRICS_SPEC §12 corrected mapping,
   2026-06-17):** The campaign JSON stores `codex_input_tokens` (noncached fresh
   input) and `codex_cache_read_input_tokens` as **separate** fields; they are not
   a total-vs-cached split. Applying the (wrong) subtraction formula
   `noncached = input - cache_read` to these fields would yield negative values and
   is incorrect. The analysis script uses the corrected mapping throughout.

4. **fix_commits=1 = `/collab` squash-commit artifact:** As noted in §3.1, the
   rework_loops delta (1.0 vs 0.0) reflects a protocol artefact, not quality.
   The METRICS_SPEC §4 increment rule counts any commit in the rework phase;
   the `/collab` protocol always traverses `CodeReviewFixGlobalPending` and
   produces at least one commit there even with zero review findings.

5. **Cache priming asymmetry:** The superpowers arm started from a warm claude CLI
   process with some cached context; the ironmem `/collab` arm accumulated a larger
   cache corpus across planning and implementation turns. The two arms had different
   cache hit rates by design (different workflows), not by accident. This is a
   consequence of the workflow asymmetry (§4, Confound 2), not an independent factor.

6. **Sample size:** n=8 tasks per arm meets the §11.3 floor for reportability but
   provides only limited statistical power. Per-task ratios range from 3.7× to 57×
   (§3.2), indicating high task-level variance. Mean comparisons at n=8 should be
   treated as indicative, not definitive.

7. **Missing transcript rows:** No rows in the campaign JSON have `estimated: true`.
   The evidence class is consistently `live`. No transcript-token gap was detected
   during the campaign.

8. **Corpus authenticity:** Corpus task authenticity (C4: each task is genuine backlog,
   not a synthetic puzzle) was verified manually at PR review per the abeval README.
   The corpus is frozen at `benchmarks/abeval/corpus/tasks.jsonl`.

## §7 — Fair follow-up experiment

The clean experiment that would isolate memory effects is a **matched-pair arm**:

| Dimension | memory-on arm | memory-off arm |
|-----------|---------------|----------------|
| Harness | `claude -p` | `claude -p` |
| Actors | Claude only | Claude only |
| ironmem MCP | enabled (memory on) | disabled / empty config |
| `/collab` protocol | **absent** | absent |

This design holds harness, model, and actor-count constant and varies only the presence
of the ironmem MCP server. It would produce a token delta attributable to memory access
overhead and recall quality, decoupled from `/collab` workflow overhead.

**Implementation:** requires runner changes to define the matched commands and MCP
configuration plus a corpus re-pin (to set a fresh `base_commit` for the new run). The
analysis scripts in this branch are forward-compatible with that design (they read
per-row fields from the JSON and make no assumptions about which arm ran `/collab`).

This experiment is **deferred**; no paid run is approved here.
